## Milestone 2 — Per-category density controls — complete

**Delivered:** v0.2.2

Dynamic Webs now resolves abundance independently for corner, span, ground and future carpet web categories while preserving the original combined density flag as a backwards-compatible fallback.

### Delivered Scene controls

The standalone Scene Configuration tab contains one labelled discrete slider for each category:

- Corner-web density
- Span-web density
- Ground-web density
- Carpet-web density

Every slider uses the shared ordered JSON-authored states:

```text
disabled → sparse → standard → dense → infested
```

The current state is displayed beside each slider. The carpet slider is persisted now but remains generation-dormant until web carpets are implemented.

### Delivered persistence and migration

Independent Scene flags are:

```text
flags.dynamic-webs.cornerWebDensity
flags.dynamic-webs.spanWebDensity
flags.dynamic-webs.groundWebDensity
flags.dynamic-webs.carpetWebDensity
```

The original flag remains supported:

```text
flags.dynamic-webs.webDensity
```

Migration behaviour is non-destructive:

- Existing Scenes with only `webDensity` resolve every available category from that value.
- The UI reports whether each value is explicit or inherited from the legacy fallback.
- Saving the Scene Configuration form persists all four category-specific values.
- A category set to `disabled` produces no webs of that category without disabling others.
- An active carpet value is stored but cannot keep the current population active by itself.

### Delivered generation contract

- Corner density selects the preset-owned corner maximum count.
- Span density selects maximum count and minimum spacing together.
- Ground density selects the ground-web count.
- Carpet density is absence-safe until carpet-specific coverage presets exist.
- Category changes are generation changes rather than presentation redraws.
- Independent category random streams remain unchanged.
- Changing one category reproduces identical web IDs, strand IDs, points and canonical projections for unrelated categories.
- Changing one category density must preserve unrelated category geometry and identifiers.

### Public API

```javascript
dynamicWebs.api.scene.getCategoryDensities();
dynamicWebs.api.scene.getCategoryDensity("wall-corner");

await dynamicWebs.api.scene.setCategoryDensity("wall-span", "dense");
await dynamicWebs.api.scene.setCategoryDensities({
  "wall-corner": "dense",
  "wall-span": "sparse",
  ground: "infested",
  "web-carpet": "disabled"
});
```

Batch mutations use one Scene update when available. Public category identifiers match the web-kind contract.

### Diagnostics and tests

Diagnostics report:

- Resolved density state for every category
- Explicit versus legacy-fallback source for every category
- Generated counts by category
- Category-specific generation reasons through lifecycle telemetry

Regression coverage confirms:

- Legacy Scenes preserve their initial category output.
- Every slider accepts only the five supported states.
- Disabling one category leaves unrelated categories active.
- Unchanged categories retain identical geometry and identifiers.
- Repeated saves replace rather than stack rendering.
- Carpet density remains dormant and absence-safe.

### Exit criteria — met

- Corner, span and ground density are independently selectable through labelled sliders.
- Every implemented category can be disabled independently.
- Existing `webDensity` Scenes migrate without changing initial output.
- Unchanged categories retain deterministic geometry and stable identifiers.
- The data, UI and API contracts include a separate future carpet-density slider.

## Milestone 3 — Level-aware web populations — complete

**Delivered:** v0.3.0

Dynamic Webs now generates, stores and diagnoses independent web populations for every detected level.

### Delivered provider policy

The world-scoped **Level Awareness Provider** setting mirrors Ambient Critters' interface and availability rules:

- Foundry v14 and later hide the setting and use native Scene elevation automatically.
- Foundry v13 with theripper93's Levels active offers `Base Level only` and `theripper93's Levels`.
- Foundry v13 without Levels shows one disabled, visually muted `Base Level only` selector.
- Base Level is the default; v13 does not opt into Levels until the GM selects it.
- Provider-specific hint text explains the detected setup.

The internal compatibility contract retains `auto`, `native-v14`, `levels-v13` and `base` for diagnostics and pre-release programmatic compatibility, but only valid user choices are exposed in Game Settings. Unavailable stored values are normalised safely. Foundry v14 never uses Levels as its active provider.

### Delivered generation contract

- Every detected level receives the complete selected corner, span and ground allocation.
- Counts are not divided between levels.

For the current `dense` presets, every detected level can independently receive:

- Up to 48 corner webs
- Up to 10 span webs
- 10 ground webs
- Structural walls are grouped by level before corner or span candidate discovery.
- Supporting walls for a web must belong to the web's level.
- Ground populations are generated independently for each level.
- Editing one level leaves unrelated level projections unchanged.
- Blueprint schema version `3` adds immutable `levelProviderMode`, `levelId` and `elevationBand`.
- Web IDs now include the stable level identifier.
- Seed version `v3` isolates every level/category pair.

```text
dynamic-webs:web-generation:v3:<scene-id>:<encoded-level-id>:<web-kind>
```

### Delivered runtime and visibility

- The runtime stores all generated level blueprints.
- GMs and players see the active viewed level and every detected level below it; levels above remain hidden.
- Viewed-level switching redraws the subset without advancing generation identity.
- Foundry v14 level-document changes and v13 Levels view changes are lifecycle-aware.
- Global provider changes regenerate the active Scene once.

### Diagnostics and tests

Diagnostics report requested/resolved provider modes, availability, fallbacks, levels, elevation bands, walls by level, visible level IDs, stored/rendered counts and cross-level support violations.

Regression coverage includes world settings, v13/v14 providers, per-level allocation, same-level support, level-isolated determinism and visibility-only redraws.

### Exit criteria — met

- Every blueprint has immutable level ownership.
- Multi-level Scenes generate independent full populations.
- GM and player rendering both respect the viewed level.
- Webs assigned to inactive elevation bands remain hidden without discarding stored geometry.
- Level switching does not regenerate unchanged geometry.

## Milestone 4 — Region-aware webs — complete

**Delivered:** v0.4.0

Dynamic Webs now applies population-owned Region restrictions using the same comma/newline tag-entry experience as Ambient Critters while retaining a standalone configuration and runtime boundary.

### Delivered configuration

Each web population stores:

```javascript
{
  confineRegionTags: ["crypt", "area-*"],
  excludeRegionTags: ["altar"]
}
```

- Confine tags use OR semantics.
- Exclude Regions subtract from the allowed area and always take precedence.
- Exact tag reuse between Confine and Exclude is rejected.
- Wildcards are supported in population role tags.
- Empty lists preserve unrestricted v0.3.1 generation and identifiers.

Dynamic Webs stores its own Region tags in `flags.dynamic-webs.regionTags` and also recognises `flags.ambient-critters.regionTags` without importing Ambient Critters internals.

### Delivered generation contract

- Region documents are collected through Foundry v13/v14 compatibility adapters.
- Region level IDs and elevation bands are matched against the selected population level.
- Rectangle, ellipse and polygon geometry is normalised into plain immutable records.
- Complete generated strand polylines must remain inside the union of matching Confine Regions.
- Any strand contact with an Exclude Region rejects the complete candidate.
- Foundry native Region containment is authoritative when available, with plain-shape compatibility fallbacks.
- Candidate filtering occurs before category count selection.
- Restricted ground generation uses a deterministic bounded candidate stream.
- Matching Region IDs and tags are recorded on blueprint schema version `5`.
- Non-matching and unrelated Regions do not affect an unrestricted population.
- Web strands are rejected rather than clipped at Region boundaries.

### Delivered UI and lifecycle

- Population cards contain a collapsed **Regions** section with Confine and Exclude textareas.
- Region Configuration contains a Dynamic Webs tag tab.
- Region creation, deletion, shape changes, elevation changes and recognised tag changes schedule deterministic regeneration.
- Diagnostics report matched, missing and level-incompatible Regions per population.

### Deferred by design

- Per-category Region fields
- Region priority or hierarchy
- Region-owned colour, density or thickness overrides
- Strand clipping
- Boundary-following web carpets

### Exit criteria — met

- Confine and Exclude Regions behave predictably.
- Exclude precedence is explicit and tested.
- Region matching is level-compatible.
- Ambient Critters and Dynamic Webs can reuse the same authored Region tags.
- Unrestricted population geometry and identifiers remain stable.
- Region ownership is immutable and diagnostic.

## Milestone 5 — Spatial index and read-only query API — complete

**Delivered:** v0.5.0

Dynamic Webs now maintains a runtime-only uniform-grid broad-phase over every stored immutable web blueprint. The index is independent of rendering visibility and exposes only deeply frozen plain snapshots.

### Delivered internal index

- Web bounds, strand centreline bounds and interaction-width-expanded strand bounds
- Perch points
- Level and elevation-band ownership
- Population and web-category ownership
- Region IDs and tags
- Strand roles and functional interaction widths
- Stable opaque identifiers
- Provisional intact state for later mutable-state filtering
- Configurable cell size derived from the active Scene grid
- Stable distance-and-identifier result ordering

The index is constructed after deterministic generation and committed only after rendering succeeds. It is cleared on Scene replacement, canvas teardown and module disposal. Colour and thickness remapping refresh immutable web snapshots without rebuilding cells. Viewed-level changes do not touch the index.

### Delivered public API

```javascript
dynamicWebs.api.getWebs();
dynamicWebs.api.getWeb(webId);
dynamicWebs.api.queryNearby(point, options);
dynamicWebs.api.queryStrands(bounds, options);
dynamicWebs.api.findCompatibleWebs(options);
dynamicWebs.api.findPerches(options);
dynamicWebs.api.spatial.getDiagnostics();
```

Queries support explicit filters for level ID, elevation point or band, population, web category, Region ID or tag, strand role, minimum functional interaction width, maximum distance, intact-only state and result limit. Spatial queries always operate over all stored levels; consumers must request physical level compatibility explicitly rather than infer it from cumulative rendering visibility.

### Delivered diagnostics and regression coverage

Diagnostics report index revision, snapshot revision, cell size, build duration, web/strand/perch counts, occupied-cell counts, cell-reference counts, query totals and the last broad-phase candidate/result counts. Synthetic dense-scene tests verify that local rectangle queries inspect only nearby cell candidates rather than scanning every indexed strand.

### Exit criteria — met

- Spatial queries use a cell broad-phase before precise checks.
- Public results are deeply immutable and contain no internal Maps, Sets or PIXI references.
- Level and elevation compatibility are explicit and tested.
- Result ordering is stable.
- The API is sufficient for later Ambient Critters integration and token-intersection work without internal imports.

## Milestone 6 — Web carpets — complete

**Delivered:** v0.6.0

Dynamic Webs now implements area-based Region-owned carpets from a deterministic composition of bundled transparent WebP patch assets.

### Delivered asset pipeline

Development-only Python tooling under `tools/asset_generation/` generates and validates the original asset library. Runtime assets are committed as lossless transparent WebP files under:

```text
assets/web-carpet/generated/
```

The checked-in manifest owns asset IDs, categories, module paths, hashes, dimensions, selection weights, recommended scale and alpha ranges, rotation and flip permissions, and tintability.

The authored atlas currently contains:

- Loose fibre networks
- Long support arcs
- Dense knots
- Edge frays
- Faint sheet fragments

### Delivered generation model

- `web-carpet` is an implemented category with the same `disabled`, `sparse`, `standard`, `dense` and `infested` states as the dynamic line-web categories.
- Carpets require at least one matching same-level Confine Region.
- One immutable carpet blueprint is created per matching Confine Region.
- Exclude Regions subtract from the final visual mask.
- Density presets control patches per grid square, maximum patches per Region and minimum patch-centre separation.
- Each patch descriptor stores a stable patch ID, WebP asset path, centre, dimensions, rotation, flips and alpha.
- Patch selection and transforms use an isolated `web-carpet` seed stream.
- Equivalent Scene, population, level, Region geometry and density inputs reproduce equivalent descriptors.

### Delivered rendering model

- At v0.6.0, corner, span and ground webs remained dynamic PIXI.Graphics line geometry; v0.7.0 later added hybrid corner and span asset presentation without changing their authoritative procedural geometry.
- Carpet WebPs are loaded through Foundry's namespaced canvas texture loader.
- Source assets are transparent white and use the population's decorative colour as a PIXI tint.
- Patches are not stretched as one full-Region image; several local asymmetric components overlap.
- A compact Canvas 2D alpha mask clips the patch container to rectangle, ellipse or polygon Confine shapes.
- Exclude shapes are removed with native `destination-out` composition.
- The mask long edge defaults to 512 pixels and is independent of WebP source resolution.
- Immutable mask keys allow Region masks to persist across visibility and presentation redraws.
- No `RegionDocument#testPoint` call occurs for each mask pixel.
- No GM baking, upload, persistent storage or per-Scene generated image manifest is required.

### Delivered cache controls

The GM-only **Clear Web Carpet Texture Cache** world setting broadcasts a local cache reset to connected clients and redraws the current visible subset. It clears Dynamic Webs' WebP request and generated Region-mask caches without changing:

- Scene populations
- Region configuration
- Immutable web blueprints
- Spatial geometry
- Corner webs
- Span webs
- Ground webs

The same operation is exposed as:

```javascript
dynamicWebs.api.webs.clearCarpetTextureCache();
```

### Spatial contract

Carpet blueprints are indexed as Region-bounded webs. Decorative WebP fibres are presentation assets rather than fabricated functional strand geometry, so strand queries continue to return only genuine generated strands. Deliberate carpet support strands may be added during the later interaction pass when their physical meaning is defined.

### Exit criteria — met

- Carpets follow Confine Region boundaries and respect Exclude Regions.
- Reusable components remain visually asymmetric and tintable.
- Dense carpets avoid procedural per-pixel JavaScript raster generation.
- First use requires only ordinary WebP loading and one compact native vector mask.
- Level switches reuse loaded patch assets and mask textures.
- Equivalent inputs reproduce equivalent carpet recipes.
- Corner, span and ground generation remains unchanged and dynamic.

## Milestone 7.1 — Persistent span-destruction hardening — complete

Destroyed wall-span state is now a compact Scene-owned deviation from deterministic geometry:

```javascript
{
  schemaVersion: 1,
  revision: 7,
  destroyedWebIds: ["<stable-wall-span-web-id>"]
}
```

The runtime loads this flag before first rendering, filters it to generated wall spans, preserves compatible IDs across regeneration and writes pruned state back through the GM. Mutations remain synchronous for interaction callers while Scene persistence is serialised through a coalescing asynchronous queue. Persistence failures are diagnostic and do not corrupt immutable geometry or the current authoritative runtime state.

Corner, ground and carpet webs remain ineligible for token destruction and cannot enter the persisted ID set.

### Exit criteria — met

- Destroyed spans remain absent after Scene reopening and server restart.
- Persistence stores no geometry, texture, population or PIXI data.
- Reset and restoration advance the revision and persist an empty or reduced ID list.
- Missing IDs are pruned after wall, Region or population changes.
- Scene flag updates redraw mutable state without regenerating geometry.
- Player clients converge through both socket snapshots and Foundry Scene updates.

## Milestone 7.2 — Categorised GM defaults and Scene span reach — complete

### Population-default contract

- Existing populations and explicit empty arrays remain unchanged.

## Milestone 8 — Scene wall-span behaviour and derived walls — complete

**Delivered:** post-v0.7.0 implementation baseline

This milestone adds opt-in Foundry wall behaviour to intact **wall-span webs only**. Corner, ground and carpet webs remain visual and do not create WallDocuments.

### Scene controls

One collapsed **Span behaviour** section appears below the population cards and stores a compact Scene-wide policy:

- Maximum span width using either the world default or a Scene override
- Vision mode: `none`, `limited` or `blocked`
- Optional movement blocking represented only as a closed secret door
- Destructible or indestructible span webs

The authored world defaults are limited vision, no secret door and destructible spans.

### Derived-wall contract

- No vision and no secret door creates no WallDocument.
- Limited vision creates a limited-sight wall with no movement restriction.
- Blocked vision creates a normal-sight wall with no movement restriction.
- Movement blocking is available only through a module-owned closed secret door.
- Vision and secret-door movement behaviour remain independently selectable.
- One stable derived wall is reconciled per intact wall-span web.
- Destroying a span removes its derived wall immediately unless that wall is an already-open generated secret door.
- An already-open generated secret door is retained as a harmless deferred-cleanup wall during token movement, avoiding Foundry's expensive perception rebuild.
- Full reconciliation, Scene maintenance or world maintenance deletes deferred walls.
- Restoring a span closes and reuses a deferred generated secret door, or recreates the wall when absent.
- An opened secret door retains its door state during ordinary reconciliation while the span remains intact.

### Maintenance controls

- Foundry's standard Configure Settings page includes **Restore Destroyed Span Webs in All Scenes**. The active Scene uses incremental runtime restoration; inactive Scenes clear only compact persistent state and remove retained generated walls, without generating geometry until those Scenes are next opened.
- **Destroy All Lingering Web Walls** scans every Scene and deletes walls tied to destroyed spans, duplicate walls and malformed generated walls while preserving one valid wall for each intact span.
- **Clear All Webs and Prepare for Uninstall** requires typed confirmation, deletes all generated web walls, removes Dynamic Webs Region flags, clears the remaining Dynamic Webs Scene flags, and leaves an explicit empty population array on each Scene so webs cannot reappear before uninstall, and clears the active runtime.
- Scene Configuration includes **Restore Destroyed Span Webs**, **Update Web Walls** and **Delete Web Walls** inside the existing Span behaviour section. Restore works for active and inactive Scenes; Update performs full active-Scene reconciliation; Delete removes generated WallDocuments without changing web populations or destroyed-span state.

### Feedback prevention

Every generated wall carries explicit Dynamic Webs ownership and source-web flags. Structural wall collection excludes generated walls before corner or span candidate detection. Wall create, update and delete lifecycle hooks also ignore them. Repeated reconciliation therefore cannot create recursive webs or duplicate derived walls.

### Destructibility contract

- Destructible spans retain the existing GM-authoritative swept token interaction and compact Scene persistence.
- Indestructible spans are excluded from local movement handling and player socket requests.
- Switching a Scene to indestructible restores persisted destroyed spans, clears their IDs and repairs the Scene flag.
- Corner, ground and carpet webs remain permanently ineligible for destruction.

### Level compatibility

- Base-level walls use ordinary Foundry wall data.
- Foundry v13 Levels walls receive compatible level and wall-height flags.
- Foundry v14 walls receive native level identifiers.
- Generated walls retain the source span's level identity.

### Regression coverage

- Vision-only walls never block movement.
- Movement blocking is emitted only as a secret door.
- Full, limited and absent vision map to their intended wall senses.
- Generated walls are excluded from source-wall collection and lifecycle rebuilds.
- Repeated synchronisation creates no duplicates and removes stale walls.
- Non-GM clients never create, update or delete generated walls.
- Indestructible state restores persisted spans and blocks future destruction.

### Release validation still required

- Live Foundry v13 verification with Base Level and theripper93's Levels.
- Live Foundry v14 verification with native Scene elevation.
- Multiplayer verification of player vision, secret-door movement and mutable-state convergence.
- Confirm the generated-wall presentation and cleanup behaviour through Scene changes and module upgrades.

## Milestone 9 — Extended token and strand interactions

**Target:** v0.9.0 or later

Whole wall-span destruction on swept token movement is complete in v0.7.0. This milestone extends that baseline to configurable policies and eventual strand-level damage.

### Detection model

Use the token’s swept movement path rather than checking only its final position.

Processing sequence:

1. Determine the token’s previous and new position.
2. Build swept movement bounds.
3. Query nearby compatible strands.
4. Filter candidates by level and elevation.
5. Perform precise segment or curve intersection tests.
6. Apply a generic interaction policy.
7. Break eligible strands through the mutable-state API.
8. Emit generic hooks and outcomes.

### Initial policy options

Support Scene-level behaviour such as:

- Ignore tokens
- Break on movement
- Break only above a minimum token size
- Break only above a minimum movement distance
- Break only selected strand roles
- Preserve structural strands
- Collapse a web when structural integrity falls below a threshold
- Separate ordinary movement and teleport behaviour

### Generic outcomes

- `NO_INTERACTION`
- `TRAVERSED`
- `STRAND_BROKEN`
- `WEB_COLLAPSED`
- `PASSAGE_BLOCKED`

### Authority and synchronisation rules

- The GM should be authoritative for mutations.
- Non-GM clients may request a mutation but must not independently commit persistent state.
- Drag previews must not mutate webs.
- Duplicate movement updates must not repeatedly break the same strand.
- Undoing token movement must not automatically restore webs.
- Teleport interaction must follow an explicit policy.
- Hidden token behaviour must be defined.
- Paused-game behaviour must be defined.

### Existing generic hook baseline

Milestone 8.1 already delivers generic immutable entity/web interaction hooks. This milestone must extend those contracts rather than introduce a second incompatible event family. Future strand-damage payloads may add strand-level detail under a versioned additive schema.

### Exit criteria

- Ordinary token movement can break intersected strands.
- Level-incompatible tokens cannot affect webs.
- Drag previews do not mutate state.
- Duplicate updates are idempotent.
- Mutation authority is consistent across clients.

## Milestone 10 — Extended persistence and network state

**Target:** v0.10.0

Whole-span Scene persistence and socket convergence were delivered in Milestone 7.1. This later milestone applies the same compact, revisioned model to future individual-strand damage, integrity thresholds, trapping and occupancy once those state types exist.

### Implement

- Per-web broken-strand records in addition to the existing destroyed-span ID list
- Revision checks across multiple mutable state types
- Explicit equal-revision conflict handling for multiple active GMs
- State pruning for missing web and strand identifiers
- Schema migrations beyond mutable-state schema version 1
- Reset damaged strands separately from destroyed whole spans
- Optional integrity-collapse regeneration policy
- Multi-client diagnostics covering spans, strands, trapping and occupancy

### Persistence principle

Do not persist complete generated geometry.

Persist only deviations such as:

```javascript
{
  schemaVersion: 1,
  webs: {
    "<stable-web-id>": {
      brokenStrandIds: [
        "<stable-web-qualified-strand-id-a>",
        "<stable-web-qualified-strand-id-b>"
      ],
      revision: 3
    }
  }
}
```

### Exit criteria

- Broken strands and later occupancy state survive reloads alongside destroyed spans.
- All mutable state types converge on the GM-authoritative revision.
- Equal-revision conflicts from multiple active GMs are handled predictably.
- Invalid strand and entity references are pruned safely.
- Persistence remains compact and stores no generated geometry.

## Architecture rules throughout the roadmap

Every milestone must preserve these rules:

- Deterministic generation
- No per-frame geometry generation
- Immutable geometry
- Separate mutable interaction state
- Stable web and strand identifiers
- Critter-agnostic Dynamic Webs internals
- Public API and hook integration only
- No dependency on Ambient Critters
- Foundry v13 and v14 compatibility adapters
- JSON ownership of authored configuration
- Focused services and classes rather than god files
- Frozen snapshots rather than mutable internal objects
- Module-owned web barriers must never be eligible source walls for generation
- Generated barrier lifecycle events must not trigger recursive web rebuilds
